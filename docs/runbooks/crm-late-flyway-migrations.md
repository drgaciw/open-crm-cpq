# CRM migrations V8 and V9 merged out of order

CRM migration V8 (account hierarchy) was merged after V10 and V11; V9 (territory and segment) was merged after V12 and V13. A database upgraded during that interval can have applied higher versions without V8, V9, or both. With Flyway's usual `outOfOrder=false`, the missing migrations are ignored and validation can prevent CRM startup.

The CRM Flyway migration strategy detects this specific history and applies only the ignored V8 and/or V9, preserving their existing files and checksums. It validates applied migrations first, runs no migration beyond the operator's configured target, and returns to the normal `outOfOrder=false` migration policy. Any other ignored migration fails closed for investigation. An existing baseline covering V8 or V9 and automatic baselining at version 8 or higher are rejected because the schema cannot be inferred from baseline history. A globally enabled `outOfOrder` setting, Flyway cherry-pick and skip-execution modes are rejected. Fresh databases and databases where both migrations were already applied use normal Flyway migration.

Roll out with older CRM replicas quiesced and drained so they do not race a new schema migration. Before rollout, inspect `crm.flyway_schema_history` and back up the CRM database using the normal operational procedure. If Flyway reports an unexpected ignored migration, a checksum error, failed migration, manually baselined schema, or a pre-existing incompatible object, stop and investigate; do not use Flyway repair or manually modify migration history as a substitute. Verify the resulting history, schema and application health after rollout. No production database has been inspected by this change.

V8 and V9 are separate Flyway migrations: if V8 commits and V9 fails, V8 remains applied. Resolve the actual schema conflict, then retry; the recovery will apply only the still-missing migration. Do not drop or modify production objects without investigating their ownership and data.
