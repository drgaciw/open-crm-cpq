# Account merge safety hold

Account merge requires a verified human JWT with `ROLE_SALES_OPS_ACCOUNT_MERGE`. Even with that role, the merge service returns `ACCOUNT_MERGE_HOLD` (503) before reading accounts or changing data. There is no runtime switch. Tenant/account scope and durable downstream quote and contract reconciliation are not implemented, and opaque customer IDs must not be guessed as account UUIDs. A later implementation must deliver and validate those prerequisites before changing the readiness policy.

The local preparation locks both organizations in numeric order. A PostgreSQL trigger locks and verifies the target organization when contacts, leads or deals acquire a new or changed organization reference. This guard affects every such CRM write, not only merge. Legacy links are left untouched; the guard returns an actionable `ORGANIZATION_REFERENCE_INACTIVE` 409 for rejected references. A mixed-version deployment remains unsafe because older merge instances do not honor the hold or locking protocol: stop merge traffic and drain old replicas before relying on the hold. This preparation does not reconcile existing history or make account merging ready to enable.

Apply CRM migrations in version order V8 → V9 → V10 → V11, after confirming which versions are already installed in each environment. Flyway does not normally apply an older migration introduced after a newer one; do not assume later delivery of V8 or V9 will be applied automatically. Reconcile migration history before rollout.

Merge locks organizations in ascending numeric ID order. Child inserts or reassignments acquire an organization share lock in their transaction. A transaction that already holds a child-row lock before requesting the organization lock can deadlock against a merge that holds the organization lock and then updates that child; PostgreSQL aborts one transaction. Callers must retry aborted transactions after re-reading current account state. This lock-order risk and the broad trigger impact require production-scale review and testing before removing the hold.

The merge rejects a dirty request-bound persistence context with `ACCOUNT_MERGE_DIRTY_CONTEXT` before locking or refreshing accounts, to avoid losing pending caller edits. If called inside an existing transaction, the failure marks that transaction rollback-only; callers must finish or roll back prior work before retrying.
